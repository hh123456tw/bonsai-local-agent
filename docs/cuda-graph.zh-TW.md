# CUDA Graph 與context取捨實測

2026-11-03。GPU為RTX3080 12GB；DFlash2 draft3、rk2v4-e8、思考預算1536、prefill256、4GiB host cache，單請求。沒有編譯新引擎。

## 同一144K配置，只切Graph

開／關交替三次啟動，各三次成功；每次三個256 token短題樣本，共各九樣本。思考關閉，中位生成速度 **189.57 → 209.25 tok/s，約+10.4%**。同一13萬token輸入，整輪 **109.172 → 111.438秒**，沒有首讀加速。兩者都在最後一題中段隨機記錄誤答，Graph沒有修復長文品質。

另做Claude Code任務時，144K開Graph第一次啟動因runtime預留不足失敗：需2,852,387,840 bytes，僅2,694,217,728可用，缺約151MiB；稍後重試成功。這是容量錯誤，不是graph-update錯誤。原失敗保留，不能只報最初3/3成功。

## 少16K容量換Graph餘裕

| 配置 | context與KV | 短題中位tok/s | 執行區預算 |
|---|---:|---:|---:|
| 原配置，Graph關 | 147456 | 190.03 | 2.19GiB |
| 相同144K，Graph開 | 147456 | 209.25 | 2.66GiB |
| 新候選128K，Graph開 | 131072 | 208.92 | 2.45GiB |

128K比144K少16,384 token，約11.1%；相對原配置的短題生成約+9.9%。主要收益來自Graph；減少KV池讓它較容易放進顯存，並沒有額外明顯提高生成速度。128K連續三次起跑成功，啟動日誌餘裕約645～668MiB；相對144K開Graph，執行區預算省約0.21GiB。

相同約10萬token輸入，原配置整輪73.86秒、128K Graph 76.234秒，兩者本次三項查找均答對。這與原13萬token題面不同，不能據此宣稱修好先前誤答。原13萬token測試再加2048輸出，超過128K總容量，不能原樣塞入新檔位。

每臂只有一題，工具路徑和授權拒絕次數不同，不能把總秒數直接算成Graph因果加速。整張GPU抽樣最低餘裕包括Windows等其他GPU活動，不能當作純引擎記憶體或精確瞬時峰值。144K關Graph一次任務也曾只剩30MiB，因此所有配置仍需留意背景GPU負載。

## 如何選

- **速度與餘裕優先**：新增「Bonsai Claude Code 加速128K」。Graph開，壓縮窗口106496；本次測試通過不代表長期穩定保證。
- **較大容量優先**：原「Bonsai Claude Code」，144K、Graph關，壓縮窗口122880；預設不變。
- **真的需要最大容量**：基本版256K，Graph關；速度較慢，長文品質限制仍在。

保留大窗口不代表每次要塞滿它；對程式Agent，先搜尋再讀相關檔案，通常比增加窗口更能降低首輪等待。Graph加速生成，不會消除長文prefill或橋接整輪緩衝。
