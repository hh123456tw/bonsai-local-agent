模型像決策者，CLI 像執行者

模型產生的 Read、Edit、Bash 是結構化指令。真正讀寫檔案的是 CLI，不是 GPU，也不是橋接。工具結果會回傳模型，再決定下一步。

啟動器負責把整套接起來

選專案 → 檢查自有服務與配置 → 必要時啟動引擎及橋接 → 真實生成健康檢查 → 用隔離環境啟動 CLI。忙碌時拒絕切換配置；兩個引擎檔位不會同時占 GPU。

這是部署與橋接專案，沒有重新訓練 Bonsai，也沒有編譯未合併的 PR #10。防循環層可以攔截特定症狀，無法讓錯誤的模型判斷自動變正確。

02 / 一次請求的生命週期

「幫我修這個錯誤」之後，
到底發生什麼事？

點選步驟查看。一次工具操作通常就需要再走一輪模型請求，所以完成任務的時間不只取決於吐字速度。

01 · CLI 把問題與上下文送出

CLI 將你的問題、系統提示、工具定義與對話歷史組成請求。Claude Code 使用 Anthropic Messages，OpenCode 使用 OpenAI Chat Completions；兩者都走8081橋接。

範例：修正版本讀取錯誤。模型先看到問題和可用工具，不會一開始就自動讀完整個硬碟。

防循環實際攔什麼？

同一輪最近兩個工具呼叫相同，模型又要求相同工具時，橋接攔下第三次，最多糾正重試兩次。簽章比較工具名稱與參數，忽略 description / timeout。仍重複或沒有效回答，就明確回報「未完成」。目前沒有總工具次數上限；若自行設回有限額度，才會另檢查次數並暫停。

為什麼仍可能「繞圈」？

A → B → A，或同一錯誤想法換不同參數，不一定符合連續重複條件；工具數量上限也不是正確性判斷。橋接是有限的保護網。反覆猜測時，應檢查實際錯誤、測試結果及檔案變更，而非只相信最後一句「完成」。

05 / 還能提升嗎？

可以。先減少白做的計算，
再調引擎參數。

目前 DFlash 已開、主機快取已擴到4 GiB。接下來最大的實用收益，往往來自少重讀、少無效工具輪次，而非繼續追短題 tok/s。

保留服務與前綴，吃到現有快取

同一任務延續原對話，避免每輪重開服務、切檔位或改動整份前置提示。能重用相同前綴時，讀取成本差很多；一旦內容或狀態不匹配，就仍需要重算。

已實測：同類13萬 token 後續追問，主機快取2→4 GiB後由約39秒降至約1.1秒。這不是普遍保證，也沒修正其中的誤答。

已配置 · 優先維持

讓 Agent 只讀需要的檔案與範圍

先搜尋檔名與錯誤位置，再讀相關函式；避免整包 node_modules、build 產物、超長日誌塞進模型。144K是能容納的上限，不是每題都要填滿的目標。

預期：降低 prefill、壓縮與錯誤診斷成本。這是基於流程的推論，尚未對你的日常專案量化加速。

可立即改用法

簡單任務考慮縮短思考，複雜修復保留

可另做思考1,024 token或關閉思考的候選配置，比較相同任務的正確率與總時間。目前仍保留1,536。當模型本來就沒用滿預算，降低上限未必會變快。

代價：基本版長文查找曾在開思考後才答對，不能只看省下幾秒。此頁沒有改動思考設定。

候選 · 未新增實測

測 prefill chunk 與 DFlash draft 長度

以現有144K或256K做基準，逐項試 chunk256→512、DFlash draft3→2或4，觀察首輪延遲、接受率、總任務時間及峰值顯存。draft更多不一定更快，驗證失敗會白做。

限制：目前餘裕不足一GiB，增加暫存可能OOM。保留原檔位回退；沒有必要為這份說明重測小context。

需控制變因測試

分階段顯示狀態，改善等待感受

可以先顯示「正在讀取／生成／檢查」，或另設計只先顯示文字、繼續緩衝工具指令的橋接。工具呼叫完成檢查前必須保留，否則會削弱現有攔截效果。

效果：讓你更早知道服務在工作；本身不會提高GPU吞吐量。選擇性串流目前未實作。

07 / 看懂專案檔案

要改哪個行為，就看哪個檔案。

repo 保存程式、設定與驗證紀錄；實際執行安裝在 C:\AI\bonsai。模型、引擎、DLL與個人聊天不提交Git。修改repo裡的檔案，不會自動更新已在記憶體執行的服務。

檔案負責什麼
start-claude.ps1桌面捷徑入口：選專案、指定檔位，交給Python啟動。
claude_launch.py準備隔離的Claude Code環境、模型ID、工具與context設定。
bonsai_ensure.py辨識自有PID、切配置、啟動引擎及橋接，驗證真實生成。
bonsai_proxy.py8081服務、共用防循環邏輯、重試、輸出緩衝與事件日誌。
anthropic_bridge.pyAnthropic文字／工具區塊、歷史檢查用轉換與SSE事件格式。生成仍走引擎原生Messages端點。
profiles/*.engine.json真正的GPU引擎參數：context、KV、DFlash、chunk與快取。
install.py / tests/ / docs/下載驗證與部署 / 橋接策略測試 / 實測紀錄及使用說明。CI只跑程式測試，不載入GPU模型。

除錯時先看安裝目錄的 engine.log（載入、顯存、生成）、proxy.log（橋接錯誤）與 guard-events.jsonl（delivered / recovery / stop等事件）。防循環事件只記錄中繼資料，不記錄完整提示或金鑰。

08 / 幾個容易搞混的名詞

Token / tok/s

模型計算文字的單位，不等於一個中文字。tok/s是每秒生成單位數，也可能包含思考，不是每秒顯示的中文字數。

Context window

一次可處理的總上下文容量，不是模型學到的知識量。系統、工具、歷史與輸出都占空間；越大不代表回答更快。

KV cache

模型對已處理 token 保存的中間注意力資料，省去部分重算。主機狀態快取還涉及其他模型狀態，並非單純把全文存成文字。

DFlash2

先提出一批候選token，再由主模型驗證。接受率高時可減少逐次生成開銷；不等於平行跑多個Agent，也不保證每題更快。

思考預算

限制單輪推理token的配置。較多不保證答對，較少也可能讓模型更容易猜錯或繞路；應用同一任務驗證。

量化 / 模型大小

這個模型檔9.52 GB，約8.87 GiB；27B指參數規模，不是27GB。其他「7G多」格式或打包不一定相同，不能只用名稱判定一致。檔案大小也不等於載入後總顯存。

為什麼有時一秒、有時等幾分鐘？

先看是否是新長文、是否重開服務或切檔位、是否正好壓縮上下文、是否重試。快取命中的短追問可以很快，但24.6萬新token的第一次讀取曾花約5分鐘。橋接又會等整輪檢查完才顯示，所以長等待不一定是服務壞掉。

防循環算修好模型了嗎？

沒有。已驗證的是特定重複呼叫會觸發糾正或停止，且一個真實編程題能完成。它不能證明任意大型任務都不會走錯，也不會修復量化或模型造成的長文查找誤答。停下來回報未完成，不能算任務成功。

為什麼沒有直接幫我改成更快？

你這次要理解專案與加速方向，因此此頁保留已通過測試的配置。chunk、draft、思考等改動需要同題比較總耗時、正確性和顯存；只追一個較漂亮的tok/s，可能讓Agent實際更慢。
